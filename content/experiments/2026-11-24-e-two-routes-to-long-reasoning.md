**이 글의 위치.** 따로 떨어진 방법이 아니라 [DecideTwice](2026-11-24-c-plan-and-replan.html)의 근거 글입니다. 역할은 "근거 분석"입니다. 긴 풀이로 들어가는 길이 둘(입력이 켜는 길, 풀다가 켜지는 길)임을 저장된 답으로 나눠 잰 분석입니다. 풀기 전과 풀다가 두 번 정한다는 설계의 근거입니다.

## 연구 질문

| 순서 | 내용 |
|---|---|
| 본 현상 | 학습 때의 입력 요소를 뺀 입력에서는 답이 "Okay"(긴 풀이의 시작 말)로 시작하는 경우가 하나도 없었습니다(0.0%). 그런데 긴 풀이로 분류되는 답은 MATH500에서 22–36%, AIME25에서 83–90%였습니다. |
| 든 의문 | 처음부터 길게 풀기로 한 답이 없는데 긴 답이 있다면, 그 답은 풀다가 길어진 것입니다. 어디서 길어지고, 무엇이 그것을 정하는가? |
| 그때까지 안 해 본 것 | 긴 풀이는 답의 첫 단어에서 정해진다고 보고 그 자리만 쟀습니다. 첫 단어는 짧은 풀이 쪽인데 뒤에서 길어지는 답을 따로 떼어 본 적이 없었습니다. |
| 그래서 한 것 | 답을 "Okay로 시작한 답"과 "풀다가 Wait가 나온 답"으로 나눠 난이도별로 셌습니다. 그리고 모델이 문제를 다 읽은 직후의 내부 상태만 보고 "이 문제는 풀다가 길어질 것"을 미리 맞힐 수 있는지 쟀습니다. |
| 답 | 긴 풀이로 들어가는 길은 둘이었습니다. 하나는 입력 요소가 켜는 길로, 쉬운 문제에서도 켜집니다. 다른 하나는 풀다가 켜지는 길로, 쉬운 문제에서는 12–17%, 어려운 문제에서는 50–61%였고 SFT, A1, QFFT가 같은 모양이었습니다. 이 길은 문제를 읽은 직후의 내부 상태로 83%까지 미리 맞힐 수 있었고, 실제로 "Wait"가 나오는 것은 그보다 600–900 tokens 뒤였습니다. |
| 다음 의문 | 모델은 풀기 전에 이미 "이 문제는 풀다가 길어질 것"을 알고 있습니다. 어려운 문제에서 긴 풀이가 필요한 때를 이 상태로 알아낼 수 있는가? ([풀이 상태를 보고 다음 행동 고르기](2026-11-24-f-state-aware-next-action.html)) |

질문의 사슬 전체는 [연구 질문으로 다시 쓴 QFFT 연구](2026-11-25-a-research-questions.html)에 있습니다.

## 메인 표: Base, SFT, A1, A2, QFFT와 추론 입력을 바꾼 조건

**표 읽는 법.** 한 줄이 "모델 + 추론 입력" 하나입니다. ACC는 정답률(%), Tokens는 답 하나의 평균 출력 tokens입니다. "구분"이 줄의 뜻입니다. 기준은 학습 방법이 다른 모델들을 표준 평가 그대로 잰 값이고, 굵게 적은 A2와 QFFT가 견줄 상대입니다. 방법은 표준 SFT를 다시 학습하지 않고 추론 입력만 바꾼 값입니다. 문제 글만 넣는 줄이 방법 QOI이고, 시스템 프롬프트만 뺀 줄은 그 부분 적용(프롬프트 템플릿은 남김)입니다. 참고는 같은 입력 변경을 다른 모델에 얹어 본 값입니다. "대기"는 지금 돌고 있는 칸입니다.

- **모델.** Base는 파인튜닝 전의 Qwen2.5-7B-Instruct입니다. 나머지는 모두 LIMO 817문항으로 학습했습니다. SFT는 QFFT 논문이 비교 기준으로 쓴 표준 SFT로, 시스템 프롬프트와 질문, 긴 풀이를 그대로 학습한 모델입니다. A1은 질문을 지우고, A2는 질문을 지우고 응답 첫 토큰의 loss까지 빼고, QFFT는 논문 방법대로 질문 없이 풀이만으로 학습한 모델입니다.
- **무엇을 견주는가.** A2와 QFFT는 학습 방법을 바꿔 새로 학습한 모델입니다. 방법 줄은 표준 SFT의 가중치를 그대로 두고 추론 입력만 바꾼 것입니다. A2나 QFFT 위에 얹은 것이 아니라, A2, QFFT와 나란히 견주는 다른 길입니다. 같은 입력 변경을 A1, A2, QFFT에 얹어 본 값은 참고 줄에 따로 두었습니다.
- **추론 입력.** 기본 프롬프트는 프롬프트 템플릿, 시스템 프롬프트 "Please reason step by step, and put your final answer within \boxed{}.", 질문으로 이루어집니다. 시스템 프롬프트 제거는 거기서 시스템 프롬프트만 뺀 입력이고, 문제 글만은 프롬프트 템플릿까지 빼고 질문 글자만 준 입력입니다. 실제 문자열은 [연구 질문 정리 글의 "실제 입력과 실제 답"](2026-11-25-a-research-questions.html)에 있습니다.
- **크기.** GSM8K 1,319문항, MATH500 500문항, AIME25 30문항입니다. 기본 프롬프트 줄은 문항마다 16회, 나머지 줄은 4회 풀게 했습니다. 최대 32,000 tokens입니다. 문제 글만 넣은 두 줄에서 † 표시가 붙은 GSM8K 값은 300문항을 2회씩 푼 값이고, AIME25는 문항마다 8회입니다.
- **채점.** GSM8K와 MATH500의 ACC는 `\boxed{}` 없이 끝난 답을 직접 읽어 반영하고, 표기만 다른 같은 답을 맞게 고친 값입니다(GSM8K는 평가 자료의 정답 16문항도 바로잡았습니다). AIME25는 공식 채점 스크립트 값 그대로입니다.
- **읽기.** MATH500에서 표준 SFT에 문제 글만 준 줄(QOI)은 ACC 81.4%, 4,221 tokens입니다. A2(81.3%, 4,587)와 QFFT(81.4%, 4,630)와 정답률이 같고 8–9% 짧습니다. GSM8K와 AIME25에서는 그렇지 않았습니다. GSM8K 300문항에서는 795 tokens로 짧아지지만 ACC가 80.5%로 내려갑니다(같은 300문항을 공식 채점만으로 견주면 표준 입력 88.7%, 문제 글만 70.2%). 상자 답을 내라는 지시가 사라져 답의 18%가 상자 없이 끝나고, 그런 답을 직접 읽어 반영해도 낮습니다. AIME25에서는 16.2%, 16,263 tokens로 표준 입력(16.7%, 20,574)의 0.74배이고, 30문항이라 정답률 차는 가려지지 않습니다. 참고 줄을 보면 A2와 QFFT도 시스템 프롬프트를 빼면 더 짧아집니다(3,948, 4,122 tokens).

## 한 줄 요약

- 긴 추론을 학습한 모델이 긴 풀이로 들어가는 길은 두 가지였습니다.
  - **단서가 켜는 길**: 응답이 "Okay, so I need to…"로 시작합니다. 쉬운 문제에서도 켜집니다.
  - **풀다가 켜지는 길**: 원래 모델처럼 "To determine…"으로 풀기 시작했다가, 도중에 "Wait"가 나오며 길어집니다.
- 학습 때의 단서(시스템 프롬프트, 프롬프트 템플릿)를 뺀 입력에서는 첫째 길이 0%입니다. 남는 것은 둘째 길뿐이고, 이 길은 SFT, A1, QFFT에서 같은 난도 곡선을 그립니다(쉬운 문제 12–17%, 어려운 문제 50–61%).
- 둘째 길은 풀기 전에 이미 예고됩니다. 문제를 읽은 직후의 모델 안 상태만으로 "이 문항은 풀다가 길어질 것"이 갈립니다(가르는 정확도 0.83). 실제로 "Wait"가 나오는 것은 그보다 600–900 tokens 뒤입니다.
- 이 예고 신호는 모델 사이에 공통입니다. SFT에서 찾은 방향을 A1에 그대로 대어도 갈립니다(0.82).

## 왜 궁금했나

- 목표로 삼은 그림은 이렇습니다. 모델이 풀기 전에 문제를 보고 얼마나 길게 풀지 정하고, 풀다가 예상과 다른 상황을 만나면 다시 정한다.
- [앞 글](2026-11-24-d-cue-ladder.html)에서 단서를 뺀 입력의 답을 직접 읽어 보니 이상한 점이 있었습니다. 긴 풀이의 표지인 "Okay"로 시작하는 답이 하나도 없는데(0.0%), 긴 풀이로 분류되는 답은 MATH500에서 22–36%, AIME25에서 83–90%였습니다.
- 긴 풀이가 처음부터 시작된 것이 아니라 풀다가 시작된 것으로 보였습니다. 그렇다면 "풀다가 다시 정한다"는 이미 모델 안에서 일어나고 있는 셈입니다. 어디서 시작되는지, 무엇이 그것을 정하는지 쟀습니다.

## 용어 풀이

| 용어 | 뜻 | 이 글에서의 실제 값 |
|---|---|---|
| 원래 모델 | 파인튜닝하기 전의 Qwen2.5-7B-Instruct | 문제를 짧게 바로 풂(MATH500 평균 534 tokens) |
| SFT, A1, QFFT | 같은 자료(LIMO)로 학습했고 학습 입력만 다른 세 모델 | SFT는 질문과 시스템 프롬프트를 모두 봄, A1은 질문 자리만 비움, QFFT는 풀이 글만 봄 |
| 단서 | 그 모델이 학습 때 늘 보던 입력 요소 | SFT에게는 프롬프트 템플릿, 시스템 프롬프트, 질문이 든 사용자 칸 |
| Okay류 시작 | 응답이 "Okay," 또는 "Alright,"로 시작하는 것 | 긴 풀이를 학습한 모델이 긴 풀이를 시작할 때의 첫 낱말 |
| 긴 풀이 (Long-CoT) | 되묻기와 다시 확인하기가 든 긴 추론 문체 | QFFT 논문의 낱말 기준("wait"가 4번 이상 등)으로 판별 |
| 첫 "wait" 자리 | 답에서 "wait"가 처음 나오는 곳 | 그 앞 글의 tokens 수 |
| 응답 시작 상태 | 문제를 다 읽고 첫 낱말을 쓰기 직전의 모델 안 숫자들 | 14번째 층의 3,584개 숫자 |
| AUC | 두 무리를 얼마나 잘 가르는지 | 0.5면 우연, 1이면 완벽 |
| 따로 떼어 둔 문항 | 방향을 찾을 때 쓰지 않은 문항 | 500문항 가운데 100문항 |
| tokens | 모델이 글을 나눠 세는 단위 | 영어 낱말 하나가 대략 1–2 tokens |

MATH500 Level 2 문항입니다.

> When the two-digit integer "AB" is cubed, the value is 912,673. What is A + B? (정답 16, 97의 세제곱이 912,673)

같은 문제를 세 모델이 어떻게 시작하는지입니다.

| 모델과 입력 | 첫머리 | 평균 길이 |
|---|---|---|
| 원래 모델, 표준 입력 | "To determine the two-digit integer AB such that its cube is 912,673, we need to find the cube root…" | 580 tokens |
| SFT, 표준 입력 (단서 있음) | "Okay, so I need to figure out the two-digit number AB such that when you cube it, you get 912,673…" | 3,770 tokens |
| SFT, 문제 글만 (단서 없음) | "To solve the problem, we need to determine the two-digit number AB such that when it is cubed, the result is 912,673…" | 두 답이 7,108과 27,715 tokens |

단서가 없는 SFT는 원래 모델처럼 시작합니다. 그런데 한참 풀다가 이런 대목이 나옵니다(688번째 token 근처).

> …So the cube must be between 20^3 = 8000 and 21^3 = 9261. **Wait**, but 21^3 is 9261, which is still less than 912,673. **Wait**, but the given number is 912,673. Hmm, maybe there's a miscalculation here. **Wait**, let's…

- 계산이 어긋난 것을 알아챈 순간부터 되묻기가 이어지고, 풀이가 길어집니다. 이 답은 "wait"가 81번 나오고 끝내 정답을 냅니다.
- 같은 문제에서 QFFT도 "To solve the problem…"으로 시작하고, 16번 가운데 8번이 풀다가 길어졌습니다. A1에서 시스템 프롬프트를 뺀 입력도 네 답 모두 "To…"로 시작했고 그 가운데 셋이 풀다가 길어졌습니다.
- Level 2의 쉬운 문제지만 모델이 풀다가 걸려 넘어지는 문제라서 길어집니다. 길이를 정하는 것이 문제의 등급이 아니라 풀이 도중의 상황이라는 예입니다.

## 무엇을 했나

1. 저장된 답 글에서 칸마다 세 가지를 냈습니다. Okay류 시작 비율, 긴 풀이 비율, 긴 풀이 답에서 첫 "wait"가 나오는 자리.
2. 긴 풀이를 두 길로 나눴습니다. Okay류로 시작한 답(첫째 길)과, 그렇지 않은데 긴 풀이가 된 답(둘째 길).
3. 문제를 읽은 직후의 모델 안 상태로 각 길을 미리 가를 수 있는지 봤습니다. 500문항 가운데 400문항에서 "그 길로 자주 가는 문항"과 "거의 안 가는 문항"의 상태 평균 차를 방향으로 잡고, 따로 떼어 둔 100문항에 대어 봤습니다.
4. 판정 기준은 계산하기 전에 연구 기록에 적었습니다. 새로 생성한 답은 없습니다.

MATH500 500문항 전체, 프롬프트 템플릿에서 시스템 프롬프트만 뺀 입력입니다(문항당 4번).

| SFT | 첫째 길 (Okay류 시작) | 62.2% | 51.1% | 49.0% | 50.0% | 41.2% |
| SFT | 둘째 길 | 17.1% | 22.5% | 29.4% | 43.0% | 60.5% |
| A1 | 둘째 길 | 12.2% | 10.7% | 21.9% | 32.0% | 49.6% |

**표 읽는 법.** 둘째 길의 값은 "Okay류로 시작하지 않은 답 가운데 긴 풀이가 된 비율"입니다. A1과 QFFT는 이 입력에서 Okay류 시작이 0%라 첫째 길 줄이 없습니다. SFT는 이 입력에 단서가 일부 남아(질문이 든 사용자 칸) 첫째 길이 절반쯤 켜집니다.

- **둘째 길은 세 모델에서 같은 곡선입니다.** 쉬운 문제에서 12–17%, 어려운 문제에서 50–61%입니다. 학습 형식이 달라도 같습니다. 앞 글의 "바닥 곡선"이 이것입니다.
- **첫째 길은 반대로 갑니다.** SFT는 쉬운 문제일수록 Okay류로 시작합니다(62% → 41%).
- 두 길이 반대로 움직여서, 둘을 합친 SFT의 긴 풀이 비율은 Level 1–3에서 평평합니다(56, 49, 54%). 시스템 프롬프트를 뺀 SFT가 "어려운 문제에만 길게 푼다"고 보기 어려웠던 까닭입니다.

### 3. 풀다가 길어질지는 풀기 전에 예고되는가

| 무엇을 가르나 | 어느 모델의 상태 | 방향을 찾은 곳 | 따로 떼어 둔 문항의 AUC |
|---|---|---|---|
| 첫째 길 (Okay류로 시작할 문항) | SFT | SFT의 다른 400문항 | 0.70 (뒤쪽 층 0.88) |
| **둘째 길 (풀다가 길어질 문항)** | SFT | SFT의 다른 240문항 | **0.83** (뒤쪽 층 0.86) |
| 둘째 길 | A1 | A1의 100문항 (한 문항씩 빼고) | 0.81 (뒤쪽 층 0.85) |
| 둘째 길 | A1 | **SFT에서 찾은 방향을 그대로** | 0.82 (뒤쪽 층 0.86) |

**표 읽는 법.** 모델이 문제를 다 읽고 첫 낱말을 쓰기 직전의 상태만 봅니다. 그 상태를 한 방향 위에 놓아 점수를 내고, 그 점수로 "그 길로 자주 가는 문항"과 "거의 안 가는 문항"을 가릅니다. 미리 정한 기준은 0.70 이상이면 "예고됨"입니다.

- **풀다가 길어질 문항은 풀기 전에 이미 갈립니다.** 실제로 "Wait"가 나오는 것은 600–900 tokens 뒤인데, 그 전에 문제를 읽은 직후의 상태에 신호가 있습니다. 미리 정한 기준으로 SFT와 A1 모두 "풀다가 켜지는 길도 풀기 전에 예고됨"입니다.
- **이 신호는 모델 사이에 공통입니다.** SFT에서 찾은 방향을 A1의 상태에 그대로 대도 A1의 문항이 갈립니다(0.82). 앞 글에서 본 "모델이 달라도 길어지는 문항이 같다"의 안쪽 근거입니다.
- 두 길의 방향은 서로 반대쪽을 향합니다(닮은 정도 −0.72). 2번 결과에서 두 길이 난도에 따라 반대로 움직인 것과 같은 이야기입니다. 그리고 한 문항이 Okay류로 시작하는 정도와 풀다가 길어지는 정도는 서로 묶이지 않습니다(문항 단위 상관 0.08).

문제 글만 넣은 입력에서 네 모델을 두 길로 나눴습니다(MATH500 100문항).

| 모델 (학습 입력에 있던 것) | Okay류 시작 (첫째 길) | 둘째 길 | 긴 풀이 비율 |
|---|---|---|---|
| SFT (프롬프트 템플릿, 시스템 프롬프트, 질문) | 0.0% | 27.0% | 27.0% |
| A1 (프롬프트 템플릿, 시스템 프롬프트) | 0.0% | 22.0% | 22.0% |

**표 읽는 법.** 네 모델 모두 프롬프트 템플릿도 시스템 프롬프트도 없이 문제 글만 받았습니다. 둘째 길은 "Okay류로 시작하지 않은 답 가운데 긴 풀이가 된 비율"입니다.

- 둘째 길은 네 모델이 같습니다(21–30%). 학습 형식과 무관합니다.
- 시스템 프롬프트 없이 학습한 모델만 문제 글만으로도 첫째 길이 절반쯤 켜집니다. AIME25에서는 75.0%, GSM8K에서는 3.0%입니다.
- 이 모델은 학습 때 시스템 프롬프트가 없었으므로, 긴 풀이와 늘 함께 있던 문제 글의 내용이 단서가 된 것으로 보입니다. 학습 자료와 닮은 대회 수학 문제에서 켜집니다. 늘 같은 시스템 프롬프트를 보고 학습한 SFT와 A1은 그 문장에 묶여, 문제 글만으로는 켜지지 않습니다.
- 이 칸은 앞 글에서 "바닥 곡선"으로 예측했다가 어긋난 칸입니다. 위 설명은 결과를 본 뒤에 붙인 것입니다.

### 5. 난도 신호는 읽히지만 길이를 정하지는 않는다 (같은 날 추가)

읽히는 신호가 실제로 길이 결정을 만드는지 보려고, 응답 시작 자리에 그 방향을 직접 더하고 뺐습니다.

| 모델과 입력 | 한 일 | 긴 풀이 비율 | 기준 칸 |
|---|---|---|---|
| SFT, 프롬프트 템플릿만 | 난도 방향 1배 더함 | 57.5% | 54.5% |
| SFT, 프롬프트 템플릿만 | 난도 방향 1배 뺌 | 58.5% | 54.5% |
| SFT, 프롬프트 템플릿만 | 같은 크기의 무작위 방향 (대조) | 57.0% | 54.5% |
| SFT, 표준 입력 | 난도 방향 1배 뺌 | 94.5% | 90.5% |
| A1, 프롬프트 템플릿만 (첫째 길 0%) | 난도 방향 1배 더함 | 24.0% | 24.0% |
| A1, 프롬프트 템플릿만 | 난도 방향 1배 뺌 | 23.5% | 24.0% |
| A1, 프롬프트 템플릿만 | **난도 방향 3배 더함** | **25.5%** | 24.0% |
| A1, 프롬프트 템플릿만 | **난도 방향 3배 뺌** | **29.0%** | 24.0% |
| (견줄 값) SFT, 프롬프트 템플릿만 | 시스템 프롬프트 방향 1배 더함 | 85.5% | 54.5% |

**표 읽는 법.** 1배는 "거의 안 길어지는 문항의 평균 상태를 거의 늘 길어지는 문항의 평균 상태로 옮기는 양"입니다. A1에는 SFT에서 찾은 방향을 그대로 썼습니다. 미리 정한 기준은 15%p 이상 늘어야 "늘어남"입니다.

- **더해도 빼도, 3배를 더하거나 빼도 미리 정한 만큼 움직이지 않습니다.** 미리 정한 기준으로 SFT는 "켜지지 않음", "꺼지지 않음", A1은 "늘지 않음", "줄지 않음"입니다. 3배를 빼면 줄지 않고 29.0%로 조금 올랐습니다(구간 21.0–37.0%, 기준 칸의 구간 16.5–32.0%와 겹침). 이 칸에서는 답의 8.0%가 "Okay,"로 시작해, 상태가 평소 범위를 벗어난 흔적도 보입니다. 답의 형식은 모두 유지됐습니다.
- 같은 자리에 시스템 프롬프트 방향을 1배 더하면 긴 풀이가 54.5%에서 85.5%로 오르는 것과 뚜렷이 다릅니다. 단서 쪽 방향은 결정을 움직이고, 난도 쪽 방향은 읽히기만 합니다.
- 그래서 이렇게 읽습니다. 모델은 풀기 전에 이 문제가 어려운지 알고 있지만, 그 앎으로 길이를 미리 정하지는 않습니다. 풀다가 실제로 걸리는 데가 생기면 그때 길어집니다. 어려운 문제에서 더 자주 걸리기 때문에, 미리 잰 난도가 결과적으로 길이를 예고하는 것입니다.
- 한계: 한 자리(마지막 입력 위치), 한 층에서 움직인 결과입니다. 난도 정보는 문제 글 전체에 실려 있어 풀이 도중 다시 읽힐 수 있습니다. 3배 크기의 무작위 방향을 더한 대조 칸도 끝났습니다(26.0%, 0배 칸 24.0% 대비 +2.0%p). 방향을 더하고 뺀 칸이 모두 무작위 방향과 같은 범위라, 미리 정한 기준으로 늘리기는 "늘지 않음", 줄이기는 "줄지 않음"입니다.

## 그래서 무슨 뜻인가

- 목표로 삼은 그림의 두 단계가 모두 모델 안에 있습니다.
  - "풀기 전에 문제를 보고 길이를 정한다": 문제를 읽은 직후의 상태에 난도 신호가 있고, 풀다가 길어질 문항을 가릅니다. 모델 사이에 공통입니다.
  - "풀다가 다시 정한다": 단서 없는 입력에서 모델은 짧게 풀기 시작하고, 걸리는 데가 생기면 되묻기 시작합니다.
- 둘은 이어져 있습니다. 미리 잰 난도가 풀다가 길어질지를 예고합니다. 다만 모델은 그 신호가 있는데도 짧은 풀이로 시작합니다.
- QFFT가 보고한 적응형 추론은 둘째 길입니다. QFFT 논문도 QFFT 모델이 짧은 풀이로 시작해 필요할 때 긴 풀이를 쓴다고 적었습니다. 여기서 새로 본 것은 세 가지입니다. 평범하게 학습한 SFT와 A1도 단서를 빼면 같은 길을 같은 비율로 간다는 것, 그 길이 풀기 전에 예고된다는 것, 예고 신호가 모델 사이에 공통이라는 것.
- 평범한 학습(SFT)이 더한 것은 첫째 길입니다. 단서를 보면 난도와 무관하게, 오히려 쉬운 문제에서 더 자주, 첫 낱말부터 긴 풀이로 들어갑니다. 적응형 추론을 해치는 것은 이 길입니다.
- 같은 날 뒤이은 실험에서 한 가지를 고칩니다. 단서는 첫째 길만 켜는 것이 아니었습니다. 응답이 원래 모델식으로 시작한 뒤에 시스템 프롬프트를 넣어도 풀다가 길어지는 답이 17%에서 76%로 늘었습니다. 단서는 둘째 길의 기준선도 낮춥니다.
- 방법 쪽으로는 이렇게 정리됩니다. 단서는 손잡이입니다. 입력에 넣고 빼면 첫째 길이 켜지고 꺼지며, 풀이 도중에 넣어도 듣습니다. 난도 신호는 손잡이가 아니라 계기판입니다. 더하고 빼도 길이는 안 바뀌지만, 생성하기 전에 "이 문제는 풀다가 길어질 것"을 0.8 넘는 정확도로 알려 줍니다. 길이를 미리 어림하는 데 쓸 수 있는지가 다음 물음입니다.

## 지금 돌리는 확인

| 실험 | 묻는 것 | 상태 |
|---|---|---|
| 문항 쪽 방향을 더하고 빼기 | 읽히기만 하는 신호인가, 실제로 길이 결정을 움직이는가. 응답 시작 자리에 그 방향을 더하면 풀다가 길어지는 답이 늘고, 빼면 주는가 | 더하기와 빼기 모두 끝남, 움직이지 않음(아래 "5. 난도 신호는 읽히지만 길이를 정하지는 않는다") |
| 풀이 도중에 시스템 프롬프트 넣기 | 짧게 풀기 시작한 답의 16, 64, 256 tokens 지점에서 시스템 프롬프트를 넣으면 긴 풀이가 뒤늦게 켜지는가 | 세 지점 모두 끝남: 16 tokens 2.19배(긴 풀이 17.3% → 76.0%), 64 tokens 1.90배(19.2% → 54.8%)는 "그 깊이에서도 켜짐", 256 tokens 1.41배(20.2% → 37.5%)는 "부분". 깊어질수록 효과는 줄어듦. 첫 낱말은 이미 지나갔으므로 풀다가 켜지는 길이 늘어난 것. 단서는 두 길 모두에 작용함([설계 글](2026-11-24-c-plan-and-replan.html)의 실험 9) |
| 다른 모델에서의 예고 신호 | QFFT와 원래 모델의 상태에서도 같은 방향으로 갈리는가. 원래 모델에서도 갈리면 파인튜닝 전부터 있던 신호다 | 끝남: SFT에서 찾은 방향이 A1 0.84, QFFT 0.86, 원래 모델 0.78로 가름(SFT 자신 0.79). 미리 정한 기준으로 "파인튜닝 전부터 있던 신호" |

## 선행 연구와의 관계

- QFFT 논문은 QFFT 모델이 짧은 풀이를 기본으로 하고 필요할 때 긴 풀이를 쓴다고 보고했습니다. 같은 관찰입니다. 다른 방식으로 학습한 모델에서 단서를 빼면 같은 모양이 나온다는 것은 그 논문에 없습니다.
- 추론 모델에서 생성 전 상태로 추론 길이가 읽히고 그 방향으로 길이를 바꿀 수 있다는 연구가 있습니다(Reasoning Strength Planning). 여기서는 긴 풀이를 두 길로 나눠 어느 쪽이 미리 읽히는지를 봤고, 풀다가 켜지는 길이 읽힌다는 것과 그 방향이 학습 형식이 다른 모델 사이에 공통이라는 것을 보탰습니다.
- 문단 경계에서 되묻기를 조절하는 방법들은 이미 있습니다. 이 글은 조절 방법이 아니라, 두 길이 무엇에 따라 켜지는지를 잰 것입니다.

## 한계

- 한 벤치마크(MATH500)와 한 학습 자료(LIMO)의 결과입니다. 모델마다 학습은 1번입니다.
- 둘째 길의 라벨은 문항당 답 2–4개로 거칩니다. SFT에서는 Okay류로 늘 시작하는 문항이 빠진 300문항만 썼습니다.
- "wait" 한 낱말로 잰 자리입니다. 단서가 있는 칸에서는 긴 풀이 문체가 첫 낱말부터 시작되므로, 두 길을 가르는 주된 표지는 Okay류 시작 여부입니다.
- 프롬프트 템플릿이 없는 입력에서는 첫째 길의 표지가 "Okay,"가 아닐 수 있습니다. 학습 문장을 문제 글 앞에 글자로 붙인 입력에서 SFT는 "I need to…", "Let me…" 같은 1인칭 혼잣말로 시작해 길게 풀었습니다("Okay," 시작은 0–12%). 그래서 문제 글만 준 칸들을 "첫머리가 1인칭인가"로 다시 확인했고, SFT, A1, QFFT 모두 0–3%로 첫째 길이 없다는 결론은 그대로였습니다.
- 읽힌다는 것은 그 신호가 결정을 만든다는 뜻이 아닙니다. 문제의 난도를 싣고 있을 뿐일 수 있습니다. 위의 더하고 빼는 실험이 이것을 가릅니다.
- 계산 도중 자체 점검 하나가 실패한 채로 계산이 먼저 돌았습니다. 점검을 고쳐 통과시킨 뒤 다시 계산했고 결과는 같았습니다.
